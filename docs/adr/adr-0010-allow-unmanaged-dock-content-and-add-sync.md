# ADR-0010: Allow unmanaged dock content and add sync

## Status

Accepted.

## Context

Issue #35 demonstrates that tools commonly create configuration directories in the dock root. Rejecting every extra entry prevents reopening otherwise valid workspaces. The old reconciliation algorithm relied on that rejection before removing entries outside desired workspace membership.

## Decision

Preserve unmanaged files, directories, and symlinks during `open`, `sync`, `add`, and `remove`. Reconcile only previously managed links, using the workspace file as configuration and the lock as derived ownership state. Recover missing links automatically; reject changed managed destinations, real entries replacing managed links, and collisions with unmanaged entries before modifying links.

Add `sync [workspace]` to perform reconciliation without opening Zed. Accept registered names and explicit paths, or infer ownership only from the current dock root. Create absent symlink-mode docks. For folder-mode workspaces, reconcile an existing dock or report that none requires synchronization. Do not adopt manual symlinks or edit workspace membership during sync.

Keep `delete` as a non-mutating preview. Explicit `delete --force` authorizes removal of the entire validated owned dock, including unmanaged contents and extra symlinks, followed by the workspace file. Never follow symlinks or delete their targets. Ownership validation remains mandatory and independent of link health or project availability. Reject execution inside the dock or its real descendants.

## Consequences

- Configuration generated by editors and agents no longer blocks opening workspaces.
- Correct symlinks stay in place, reducing disruption to active editor sessions.
- Files kept exclusively inside the dock are deleted by `delete --force`; the preview and usage documentation state this explicitly.
- Ownership checks reject symlink dock roots, non-regular locks, invalid link names, duplicate names, relative ownership/target paths, and unsupported versions.
- Lock version 1 and the persistence layout remain unchanged. Filesystem failures may interrupt removal; deletion is not transactional.

## Alternatives Considered

- Reject all extras: conflicts with routine tool behavior and issue #35.
- Prompt during open or adopt manual symlinks: disrupts automated tasks or implicitly changes ownership.
- Preserve extras after deletion: leaves unregistered content in the cache and conflicts with the selected whole-dock deletion contract.
- Restore exclusively from the lock: can resurrect projects removed from the authoritative workspace file.

## Implementation Notes

Separate ownership validation from health inspection and reconciliation. Validate conflicts before applying changes and preserve unmanaged entries during rollback. Use standard-library recursive removal without following symlinks. Keep schema resources descriptive rather than runtime validators.
